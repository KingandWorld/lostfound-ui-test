## 一、背景

- **被测系统**：失物招领系统（前后端分离，后端部署于 4G 轻量云服务器，宝塔面板 nginx 反代）。
- **测试资产**（两个独立项目，共用同一后端与测试账号）：
  - 接口自动化 `lostfound-api-test`：pytest + requests + Allure，约 52 条用例 / ~34s，**已常驻服务器 Jenkins CI**（2026-08-16，自由风格项目 `lostfound-api-test`）；
  - UI 自动化 `lostfound-ui-test`：Playwright + pytest + Allure + Page Object，21 条用例 / ~105s，**2026-08-18 起本地运行**。
- **资源约束**：服务器为 **4G 内存 + 2 vCPU 轻量云**（Ubuntu 22.04），Docker 内已常驻 Jenkins（768MiB 上限）/ 禅道（512MiB）/ 禅道数据库（256MiB）等容器，同时承载业务后端。
- **核心设计问题**：UI 测试需要 headless Chromium（单实例内存占用数百 MB），4G 服务器能否承载？CI 该怎么集成？

## 二、实测数据（2026-08-21 实测）

### 1. 服务器内存基线（UI 测试运行前）

```text
MemTotal:       3809096 kB（3.6Gi）    MemAvailable:  776552 kB（758MiB）
Swap: 2G（swapfile，当时未使用）
容器占用：jenkins 488.6MiB/768MiB · zentao 235.6MiB/512MiB · zentao-db 100.8MiB/256MiB
```

**关键结论**：容器配额合计 ~1.5G + 系统开销，**空闲可用内存仅 ~758MiB**——已低于单个 headless Chromium 的典型占用区间（300~600MB），服务器全自动运行 UI 测试的内存余量极低。

|----|----|

| 测试总耗时 | **220.70s**（本地同期 ~105s，慢约 2 倍） |
| 测试结果 | **4 failed, 15 passed, 2 skipped, 4 rerun**——2 条搜索用例 10s 响应超时失败（各重试 1 次仍失败，`--only-rerun` 超时类命中） |

| swap | 0MB 未使用 |
| OOM | 未触发（`dmesg` 无 oom/killed 记录） |

## 三、三方案对比

| 方案 | 描述 | 内存峰值 | 测试耗时 | 稳定性 | 面试展示价值 |
|------|------|----------|----------|--------|------------|
| **A：服务器全自动** | 所有测试在服务器 Jenkins headless 运行 | used 峰值 2987MB / 可用低至 414MB（实测） | **220.7s**（实测，本地 2 倍） | **差：2 条用例 10s 超时失败（实测）；与 Jenkins/业务并发时 OOM 风险高** | 高（自动化程度最高） |
| **B：本地 Agent** | 本地电脑注册为 Jenkins 从节点跑 UI 测试 | N/A（浏览器跑在本机） | 同本地 | 依赖本机在线、Agent 维护复杂 | 中（需解释架构，面试演示不便） |
| **C：混合方案** | 接口测试 CI 全自动（现状保持）；UI 测试本地一键运行 + 手动合并 Allure 报告 | 本地 headless-shell 峰值 **494MB**；**服务器零新增负担** | 本地 133.66s（零失败） | **高（本地资源充足，2026-08-18-18 全绿实测）** | 高（体现务实与资源意识） |

## 四、最终决策：方案 C（混合方案）

### 决策理由（数据 + 逻辑）

1. **内存数据不支持方案 A**：服务器空闲可用仅 ~758MiB，headless Chromium 单实例常驻 300~600MB，全量 21 条用例串行运行将长期挤压可用内存，与 Jenkins/禅道/业务后端抢资源，OOM 风险高（实测数据见第二节）；
2. **方案 B 得不偿失**：本地 Agent 虽可行，但引入"本机必须在线 + 双向 SSH + Jenkins 从节点维护"的复杂度，面试展示性也不如一个自洽的决策故事；
3. **方案 C 是资源约束下的最优折中**：接口测试（轻量、关键、可无人值守）保持全自动 CI；UI 测试（重、需要浏览器、失败需人工看截图）本地一键运行，结果手动合并——**自动化程度与资源现实的最佳平衡**；
4. **2026-08-17 预判与 2026-08-21 实测一致**：决策不是拍脑袋，是"预判 → 实测 → 数据支撑"的闭环（详见第五节决策经验沉淀）。

### 落地现状（2026-08-21）

| 落地项 | 内容 |
|--------|------|
| 接口测试 CI | **保持现状不动**：Jenkins `lostfound-api-test` 全自动（Poll SCM 每 30 分钟） |
| UI 测试本地一键脚本 | `run_ui_tests.bat`（Windows）/ `run_ui_tests.sh`（Linux/macOS）：跑测试 → 生成 Allure → 保留 history 趋势 → 本地 HTTP 打开报告 |
| Allure 报告 | 本地 `allure-report/` 独立生成；history 文件夹跨轮保留（趋势图连续）；如需与接口报告合并展示：`allure generate <接口结果目录> <UI结果目录> -o <合并目录> --clean` |
| Jenkins 手动触发 | UI 仓库建立远程（Gitee/GitHub）后，可加 Jenkins 手动触发参数 `UI_TESTS=true/false` 供"想跑就在服务器跑"的弹性（服务器内存允许时）；当前 UI 项目尚未建远程，此步暂缓 |
| 敏感信息 | 一键脚本无任何敏感信息；服务器地址/凭据只在本地 `.env`（gitignore） |

### 演进路径（什么时候升级方案）

- 服务器内存扩容（≥8G）或迁移更高配实例 → 可平滑升级方案 A（UI 测试迁入 Jenkins，本地脚本保留为调试工具）；
- 团队引入 Jenkins Agent 管理实践 → 可升级方案 B；
- 升级是"资源到位后的自然演进"，不推翻当前决策的正确性。

## 五、决策经验沉淀

**核心设计问题**："你的自动化测试是如何集成到 CI/CD 的？遇到资源限制怎么解决的？"

**决策说明**：

> 我的接口测试（约 50 条用例，30 秒跑完）已接入服务器 Jenkins 全自动 CI，配置了 Git 拉取、依赖安装、pytest 执行和 Allure 报告，每 30 分钟轮询代码变更。UI 测试是 Playwright + Page Object 的 21 条用例，需要 headless Chromium，内存占用几百 MB。我的测试服务器只有 4G 内存、可用空间不到 1G，跑 UI 测试会和 Jenkins、业务容器抢内存，有 OOM 风险。所以我采用混合方案：接口测试保持 CI 全自动，UI 测试本地一键脚本运行、生成 Allure 报告并保留历史趋势。这是我在预判后做实测验证、用数据支撑的决策。

**决策依据**：

1. **决策依据是数据不是感觉**：实测服务器空闲可用内存 ~758MiB，低于 Chromium 单实例需求；本地跑 UI 测试内存充足且 2026-08-18~20 全绿——两头数据对比，方案 C 自然胜出；
2. **体现成本意识**：不是"不能全自动"，而是"在这个资源下全自动会牺牲稳定性"；方案 A 是服务器扩容后的自然升级路径；
3. **体现工程化能力**：一键脚本（bat/sh 双平台）、Allure history 趋势保留、跨项目报告合并命令、Jenkins 手动触发参数留作弹性——不是只做选择题，还做了配套工具。

**备选方案辨析**：
- "为什么不把 UI 测试放 Docker 里限制内存跑？" → 服务器总内存 4G 是硬约束，容器限流只是"不死"，性能与稳定性仍差；且与业务后端同机抢资源风险不可控；
- "本地跑怎么保证定时回归？" → 当前阶段以"发布前手动回归"为主；服务器扩容后升级 Jenkins 全自动（演进路径已设计）；
- "CI 里接口测试和 UI 测试为什么策略不同？" → 两层测试技术栈不同：接口轻量可无人值守，UI 依赖浏览器资源且失败需要人工看现场（截图/控制台），"重测试人工、轻测试自动"是资源受限下的常见工程实践。
